# The CI test and mutation shards

This loads when you work on the workflows, the shard maps, the scripts or `codecov.yml`. The mutation shards are described at the end; the test shards first. `.github/workflows/test.yml` runs the Library suite as one `unit` job plus one job per key of `composition-shards.json`, every job through `scripts/test.cs`, so the filter, configuration, coverage and results mechanics live in one place: change them in the script, never in the YAML, and run the same script locally (`dotnet run scripts/test.cs -- --help`).

## The contract

- `unit` = `TestCategory!=Composition` on the Library suite plus the Infrastructure, App.Components and Architecture projects. It is a category clause because the NUnit adapter always honours those; any other filter that selects more than 2,000 tests is dropped silently and the whole suite runs.
- A composition shard = one `FullyQualifiedName~<fixture full name>.` clause per listed fixture, joined with `|`. The trailing dot stops a fixture matching a longer name. `CompositionShardTests` (Architecture suite, ~10 s) rejects fixtures a name filter cannot select (parameterized, sourced, generic or nested) and method-level `Composition` tags, and requires every tagged fixture in exactly one shard, every shard key in the matrix, no `unit` key, and `codecov.yml`'s `after_n_builds` (both occurrences) equal to the matrix size: Codecov counts one upload per job, so fewer posts statuses on partial coverage and more never posts.
- Every shard run passes `RunConfiguration.TreatNoTestsAsError=true` because VSTest exits 0 with a warning when a filter matches nothing; the script also refuses a shard whose list is empty.
- `dotnet run scripts/test.cs -- --verify-shards` holds the behaviour the guard cannot: it runs the unfiltered Library suite and every shard, then requires the union of executed tests to equal the full set with no test in two shards and no name-filtered shard above the adapter's 2,000-test limit (`--list-tests` cannot stand in: the adapter applies filters at execution). Run it after any change to the map, the filter derivation, or a sweep fixture's shape; it takes a few minutes.
- Every run carries VSTest's hang bound (`--blame-hang-timeout 10m`, `HangTimeout` in the script; no dump is collected). It is an inactivity timer, not a per-test one: it resets whenever any test starts or finishes, so ten minutes without either terminates the test host, and the `Sequence_*.xml` next to the trx (included in the `test-results-*` artifact) lists every test that was in flight, up to one per worker. A hang therefore fails the run in minutes instead of holding the job to its 20-minute timeout. The longest seeded sweep is about a minute on the runner; a legitimate test that approaches the bound is a test to split, not a reason to raise it. The `--blame-*` switches are VSTest's: opting `global.json` into Microsoft.Testing.Platform would mean replacing them with `--hangdump` / `--hangdump-timeout`.
- `test.yml` runs on every push and pull request, documentation-only ones included: its `test` job (which waits for the shard matrix and fails unless every shard passed; `always()`, so a shard that hits its timeout makes the check red rather than missing) is the stable check name a ruleset requires, and a required check that a path filter skips leaves the pull request pending forever. `.github/rulesets/main.json` is the ruleset for `main` — required checks `test` and `lint`, pull requests only, no force-pushes or deletion, administrators may bypass from the merge dialog — applied by hand from the repository's Rules settings or with `gh api --method POST repos/{owner}/{repo}/rulesets --input .github/rulesets/main.json`; a renamed gate job means updating the JSON and the live ruleset together, and a pull request opened before the gate existed shows `test` as expected-but-missing until it is rebased.

## Balancing

- Balance by runner time only: the public-repository runner is 4 vCPU with 4 NUnit workers and slower per core than a developer machine, so local durations mislead. Download a recent run's `test-results-*` artifacts (`gh run download <run id> --dir <dir>`) and read them with `dotnet run scripts/test.cs -- --durations <dir>`: summed seconds per fixture is a shard's load, the longest single test is its floor (a 45–55 s sweep cannot be split), and the runner varies by about ±45 s on an identical shard between runs, so stop balancing inside that tolerance.
- Each shard pays ~50 s of restore and build before its first test; a new shard is worth it only when the heaviest shard's test time exceeds that by a clear margin. Growing or shrinking the matrix means the same change to the matrix list and to both `after_n_builds` values in `codecov.yml`; the guard fails otherwise.
- A new `[Category("Composition")]` fixture goes into the lightest shard in the same PR; then run `--verify-shards` and read the shard's job time on the PR.

## The mutation shards

- `.github/workflows/mutation.yml` runs Stryker two ways: pull requests get `--since:origin/main` per test project; pushes to main that touch `src`, `tests` or the mutation tooling, and `workflow_dispatch`, run every project whole, including the full Library mutation, which is 2,424 testable mutants — hours in one job. That run is one job per key of `.github/workflows/mutation-shards.json`, each key listing top-level folders of `src/BaroquenMelody.Library` (`.` for its root files); `scripts/mutate.cs --shard <name>` turns the folders into `-m` globs anchored on the project folder (`**/BaroquenMelody.Library/<Folder>/**/*.cs`) and forwards any other argument to `dotnet stryker`, so a shard runs locally the same way (Stryker's concurrency default is half the logical processors: 8 on a 16-core machine; CI passes `-c 4` explicitly, one test run per vCPU of the public-repository runner, which is why it is not in the config files). CLI `-m` globs replace the config's `mutate` list; files outside the globs appear in a shard's report with no mutants, except that Stryker compiles every mutant before filtering, so a file can carry its compile-error mutants in every shard and the odd file carries its filtered mutants marked "Removed by mutate filter" (seen for the root `BaroquenMelodyComposerConfigurator.cs`).
- `MutationShardTests` (Architecture suite) requires every source folder in exactly one shard and every shard key under `shard:` in the workflow. A new top-level Library folder therefore goes into a shard in the same PR.
- The `library-report` job downloads the `mutation-report-library-*` artifacts and runs `scripts/mutate.cs --merge`, which drops the filter-removed mutants, takes each file from the one shard where it has tested (non-compile-error) mutants, prints the score table (appended to the step summary), fails if any file was mutated by more than one shard, and writes `StrykerOutput/library/reports/mutation-report.json`; `--upload` PUTs it to the dashboard as module `library` under the branch name. Per-shard dashboard modules were rejected: the dashboard does not aggregate modules into one score.
- The repository is public, so standard-runner minutes are free and unlimited (it was private and out of minutes on 2026-09-05, which is why the full runs were dispatch-only for a day); the bounds that remain are for wall time and hangs. Balance the shards by the library jobs' durations on a recent run — an uncovered mutant costs no test run, so the mutant counts from `--summary <report>` are only the tie-breaker; each shard pays ~5 min of build, initial test run and mutant compilation before testing starts. Pull-request legs are capped at 30 minutes (a leg that re-tests most mutants is the full run's job), and a leg first diffs its project's folders against `origin/main` and stops when nothing changed. Pull requests and pushes cancel their own superseded runs (the dashboard wants the newest main); a dispatch never does.
